# Swingle README — Adversarial Review

**Subject:** `github.com/discreteds/swingle`, README at v2.0.0
**Date:** 25 July 2026
**Stance:** Hostile reader. Every claim treated as a target. Nothing is graded on effort.

The reviewer assumed here is competent, sceptical, and has thirty seconds before deciding
the project is overclaiming. Findings are ordered by how much damage they do on first read,
not by how hard they are to fix.

---

## 1. Claims that do not survive contact

### 1.1 "LLM routers and gateways proxy your traffic and hold your keys"

**Verdict: materially false, and it is your headline.**

Three counterexamples, all trivially findable:

| Service | Why the claim fails |
| --- | --- |
| OpenRouter (credits mode) | Default operation involves no provider keys of yours at all. BYOK is opt-in. |
| Cloudflare AI Gateway | Documents a pass-through mode where the application's auth headers are forwarded untouched — nothing stored. |
| Not Diamond, Morph Router | Do not proxy the call. They return a routing decision; your process makes the request with your own SDK. |
| LiteLLM (self-hosted) | Your keys, your infrastructure, no third party in the path — the exact posture you claim as differentiated. |

The sentence is doing the most important job in the README — establishing why the category
you are compared against is the wrong category — and it is the sentence most easily
disproved. A reader who knows one of these four now discounts everything downstream,
including the claims that are true.

**Fix:** delete the key-custody argument as a primary differentiator. It is your third-best
argument at best, and it is the only one that is falsifiable.

### 1.2 "A router is a hop; Swingle is a hitch"

Good line, wrong load-bearing wall. It only works if 1.1 holds. Keep the phrasing, attach it
to a claim that survives: routers hand you a *model*; Swingle dispatches a *harness*.

### 1.3 "Nothing enters the prompt path"

**Verdict: false on the plain reading, by your own design.**

Swingle injects pack doctrine, role inference from `core/roles.md`, contracts, model-tier
selection and evidence-gate instructions into every dispatched prompt. Swingle is one of the
largest things in the prompt path. What you mean is *no third party* enters it. What you
wrote is an absolute that your own architecture section refutes two screens later.

### 1.4 "Fully local"

**Verdict: true of orchestration, false of the thing readers care about.**

Zero inference is local. Every token is generated by a remote frontier model over someone
else's network. In 2026 "fully local" reads as local weights. A reader who installs on that
basis feels misled, and the disappointment attaches to the project, not to their skim.

**Fix:** "local orchestration, no proxy, no key custody." Longer, true.

### 1.5 "Everything is self-contained. No machine-specific paths are required"

**Verdict: contradicted within the same document.**

The opencode section then requires: a script that reads Claude Code's `installed_plugins.json`
to emit pinned install paths, `XDG_CONFIG_HOME` resolution, physical-path resolution behind
symlinks, and two environment variables that can silently disable discovery. That is a
machine-specific path problem documented in detail.

The install section also opens with **"Requires the `superpowers` plugin"** — a hard
third-party dependency stated immediately after a self-containment claim. And `sdd` "wraps
`superpowers:subagent-driven-development`". A hostile reader concludes the flagship skill is
a wrapper around someone else's methodology with a manifest format bolted on.

**Fix:** "self-contained *within this repository* — no machine-specific paths in the packs
themselves," plus an explicit dependency line up front. Own the superpowers dependency
loudly; hiding it in step one of install looks worse than declaring it.

### 1.6 "Harness-neutral"

**Verdict: aspirational, not observed.**

Claude Code: two commands. Codex: two commands. opencode: a decision tree with two mutually
exclusive routes, a footgun warning about the plugin cache, a worked example of the failure
(mismatched `sdd` 1.0.0 beside `delegate` 1.5.0), two environment-variable caveats, and a
`grep`-based verification step.

The candour is admirable and reads as a weakness. Neutrality claimed in the abstract and
contradicted by 600 words of asymmetry in the concrete invites the reader to assume the
neutrality is theoretical.

### 1.7 Harness count mismatch

Front matter names six harnesses (Claude Code, Codex, opencode, agy, Grok, Pi). The
repository description names three packs (codex/opencode/agy). The reader's first exposure
to the project — the GitHub social card — disagrees with paragraph two. Pick a number and
state verification status per harness.

## 2. The evidence asymmetry

This is the finding that should sting most.

> "Token thrift is the point."

The economic claim — the entire reason the project exists — carries **no number anywhere in
the README**. No measured delta. No worked example. No before/after on a real plan.

Meanwhile the README specifies: a manifest schema with nine required fields, a validator, a
release gate, a four-level model-override precedence chain, a report-transport failure mode
documented down to "exit code stays 0", and a three-tier recording ladder for verification
findings.

The rigour is real and it is pointed entirely at CLI behaviour. The commercial claim is
asserted. A reviewer reads that asymmetry as: the author enjoys the plumbing and has not
tested the premise.

**Fix, and it outranks every wording change in this document:** one artifact showing a real
plan executed all-Opus versus tiered across harnesses, with the dispatch ledger and the cost
delta. That number does the positioning unaided.

## 3. Threat model: the small door is bolted, the barn door is undiscussed

> "Every value is validator-enforced… so a manifest can never smuggle in a command to
> execute."

Manifest injection is a narrow surface, and you have closed it competently. But the system's
actual function is to spawn agentic CLIs with **model-authored task text**, against harnesses
that edit files and run commands, with an `unsupervised` lever, a `floor it` lever, and a
`read-only` mode that is opt-in rather than default.

Unaddressed in the README:

- What an adversarial or merely confused dispatched agent can do inside a dispatch.
- What "hardened evidence gates (staged + untracked + HEAD-unchanged)" defend against, and
  what they explicitly do not. Asserting "hardened" without a threat statement is the
  security equivalent of "military-grade."
- Prompt-injection reaching a dispatched agent via repository content it is asked to read.
- The supervision default: "jobs implying ≥3 planned dispatch cycles run supervised
  automatically." *Implying* how? If a model infers it, a safety default is set by inference.
  Say so plainly or make the trigger deterministic.

The word "never" appearing in the one paragraph that addresses security, next to the one
surface that is not the dangerous one, is the sharpest single attack available against this
project. Expect it in the first serious issue you receive.

## 4. Positioning: the wrong opponent

The README spends its strongest real estate arguing against LLM routers. Nobody was going to
use OpenRouter to have Codex review a Claude Code diff — routers do not do that. Arguing
against a category the reader had not considered produces "I wasn't going to anyway," not
conviction.

The actual competitive set: Claude Code's own subagents and Task tool, opencode's multi-model
configuration, Aider's architect/editor split, and Conductor-style multi-agent orchestrators.
Not one is mentioned.

Keep the router contrast to two sentences of disambiguation. Spend the space on why
cross-harness dispatch beats staying inside one harness's own subagent system — which is the
question every prospective user will actually be asking.

## 5. The unmarked commercial risk

The differentiator with a real moat — flat-rate subscription seats instead of metered API
tokens — is also the one with terms-of-service exposure. Programmatic, unattended use of
consumer subscription seats sits near the line in most providers' acceptable-use terms, and
Anthropic shipping first-party subagents does not cover *"spawn a different vendor's CLI
unattended from inside another agent's loop."*

Two observations, neither of which is legal advice:

1. The product does not change if the framing shifts from *arbitrage* ("stop paying API
   rates") to *orchestration* ("drive the tools you already run interactively"). The
   regulatory surface changes considerably.
2. If seat-based dispatch is load-bearing for the value proposition, the README should say
   what happens when a provider closes it. A one-line degradation story (packs fall back to
   API-keyed dispatch) turns an existential risk into a configuration note.

There is a related capability gap nowhere acknowledged: every CLI must be **authenticated
once interactively**. That means no headless CI, no ephemeral runners, no unattended
scheduling without a human-seeded credential store. A router runs anywhere a secret does.
State the constraint before a user discovers it in a pipeline.

## 6. What holds up

Not a courtesy section — these survived deliberate attack:

- **"Adding a pack requires zero edits to `core/`; routing is manifest-driven."** Strong,
  falsifiable, and you ship the validator that tests it. Lead with this in the technical
  section.
- **The `report-transport` documentation.** "A report-file request fails *intermittently*
  while the exit code stays 0" is the sentence in this README that most convinces a reader
  the author has actually run the thing in anger. More of this.
- **The recording ladder.** "A finding recorded only in an installed cache is a finding
  lost" is genuinely good documentation practice and is rare in projects at this stage.
- **Harness / provider / model vocabulary discipline.** Correct, useful, and currently buried
  under the router argument. It is your differentiator, not a footnote.
- **Malformed override is a hard error, never a silent fall-through.** Good instinct, stated
  well.

## 7. Proposed rewrite of the contested paragraph

Current:

> **A router is a hop; Swingle is a hitch.** LLM routers and gateways proxy your traffic and
> hold your keys. Swingle spawns processes locally against credentials you already hold —
> local dispatch, no proxy, no key custody. Nothing enters the prompt path.

Proposed:

> **A router gives you a model; Swingle gives you a harness.** Gateways hand back tokens from
> an endpoint — the agent loop is gone: no tools, no sandbox, no file edits, no session
> resume. Swingle dispatches whole harnesses with their scaffolding intact, spawned as local
> processes against CLIs you have already authenticated. No proxy, no third party in the
> prompt path, and no second metered bill on top of the tools you already run.

Three claims, in the order they should be made: **unit of dispatch** (capability),
**substrate** (economics), **path** (trust). The current text has that order exactly
inverted.
